# Тест-дизайн BookingLab

## Классы эквивалентности и границы

| Поле/правило | Допустимо | Недопустимо и границы |
|---|---|---|
| Дата | будний день от завтра до +14 дней | сегодня, прошлое, +15, выходной, невалидная строка |
| Время | 09:00, 09:30 … 20:30; конец ≤21:00 | 08:30, 09:15, 20:30+60 |
| Длительность | 30, 60, 90, 120 | 0, 45, 150, дробь, строка |
| Участники для capacity=4 | 1, 4 | 0, 5, дробь |
| Title после trim | 3, 60 | 2, 61 |
| Вместимость комнаты | 2, 10 | 1, 11 |
| Цена комнаты, копейки | 10000, 200000 | 9999, 200001 |
| Слот | свободный, соседний [11:00,11:30) | пересечение [10:30,11:30) с [10:00,11:00) |
| JWT | валидный | отсутствует, истёк, неверный; чужая бронь → 404; USER на admin API → 403 |

## Таблица решений для создания брони

Порядок ошибок: авторизация → схема → комната существует → активна → дата/время/участники → слот свободен. Отсутствие комнаты даёт 404, неактивность 409, неверные ограничения 422, пересечение 409, свободный слот 201.

## Переходы и интеграция

Разрешены CREATED→PAYMENT_PENDING/CANCELLED/EXPIRED и PAYMENT_PENDING→CONFIRMED/PAYMENT_FAILED/CANCELLED/EXPIRED. Терминальные статусы блокируют дальнейшие действия 409. Граничный момент `now == expires_at` переводит в EXPIRED. Повтор `event_id`, чужой `booking_id`, поздний SUCCESS и FAILED→SUCCESS не меняют итог. Две конкурентные заявки на один слот в PostgreSQL должны дать один 201 и один 409. Kafka сценарии: штатная публикация/ответ, остановленный payment-service, недоступный broker, дубли. Моки: Clock и платёжный publisher, сценарии success/failure/no_response.

Локальные тесты покрывают критичные правила и обработчик результатов. Интеграционные проверки конкурентности и Kafka требуют работающего Compose и должны выполняться отдельно на изолированном наборе данных.

## Уточнённые API-контракты

- USER с `include_inactive=true` получает `200`, но только активные комнаты; GET неактивной комнаты возвращает `404 ROOM_NOT_FOUND`.
- Пустой PATCH комнаты — no-op `200`; любое явно переданное `null` — `422 VALIDATION_ERROR`. Эти правила отражены в OpenAPI.
- Health возвращает `{"status":"ok"}` при успехе; readiness при недоступной БД возвращает `503 DATABASE_UNAVAILABLE`. Kafka и payment-service readiness не блокируют.
- Пагинации в MVP нет. Списки проверяются на малом контролируемом наборе: фильтрация по роли и документированная сортировка.
- Для проигнорированных payment events проверяется отсутствие изменения состояния. Наличие лога проверяется по структурированным полям `event` и `reason`, без привязки к тексту.
