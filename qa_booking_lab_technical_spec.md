# Техническое задание: BookingLab

**Версия:** 1.1  
**Назначение:** учебное веб-приложение для практики автоматизации тестирования (API, UI, БД, авторизация, интеграция через Kafka и моки).  
**Объём:** маленький проект, который можно покрыть основным набором автотестов за 1–2 недели.  
**Приоритет:** однозначность и проверяемость требований, а не коммерческая полнота.

## 1. Концепция и границы

BookingLab — сервис бронирования переговорных комнат. Пользователь регистрируется, выбирает комнату и бронирует временной интервал, после чего может инициировать **симуляцию** оплаты. Администратор управляет комнатами. Реальных денег, платёжных реквизитов и стороннего эквайринга нет.

**Три связанные бизнес-сущности:** `User` → `Booking` → `Room` (у пользователя много броней; у комнаты много броней). **Отдельный микросервис:** `payment-service` (симулятор оплаты), общение через Kafka. Микросервис и брокер необязательны для запуска основного приложения.

**Не входит в MVP:** восстановление пароля, почта, аватары, промокоды, возвраты, сложный календарь, реальные платежи, refresh-токены, уведомления, мультивалютность, мобильное приложение, Kubernetes.

## 2. Технологии и структура

- `frontend`: React + TypeScript + Vite; семантический HTML, простые формы; порт `http://localhost:5173`.
- `backend`: Python + FastAPI + Pydantic + SQLAlchemy + Alembic; REST/OpenAPI; порт `http://localhost:8000`.
- `db`: PostgreSQL (данные основного приложения, миграции).
- `payment-service`: отдельное приложение Python/FastAPI с Kafka consumer/producer; имитирует исход оплаты; без обращения к основной БД.
- `kafka`: Kafka-совместимый брокер (допустим Redpanda в режиме Kafka API), запускаемый **только** с Docker Compose profile `payments`.
- Весь стек запускается в Docker Compose; у каждого приложения свой `Dockerfile`. Исходники фронта и бэка — разные каталоги, тесты — отдельно.
- Базовый стек должен собираться и работать без установленного на хосте Python, Node.js и PostgreSQL (требуется Docker/Compose).

### Режимы оплаты

`PAYMENT_MODE=stub` (**по умолчанию**): основное приложение самостоятельно генерирует тестовый результат оплаты через тот же обработчик, что используется для Kafka-события. Kafka и payment-service не требуются.

`PAYMENT_MODE=kafka`: backend формирует запрос в Kafka, `payment-service` получает его и отправляет ответное событие. При недоступности брокера основной backend не падает; создание, чтение и отмена броней продолжают работать. Незавершённые оплаты остаются ожидающими до истечения срока.

`PAYMENT_MODE=disabled`: `/pay` возвращает `503 PAYMENTS_UNAVAILABLE`, остальные функции работают.

Конфигурация меняется переменными окружения без изменения кода. Backend **никогда** не имеет `depends_on: payment-service` или обязательной зависимости готовности Kafka для запуска.

## 3. Роли и авторизация

- `USER`: регистрация, вход, список активных комнат, создание и просмотр **только своих** броней, оплата/отмена своих броней.
- `ADMIN`: права `USER`, создание/изменение/деактивация комнат; просмотр всех броней.
- Регистрация `POST /api/auth/register` всегда создаёт роль `USER`; поле `role` в запросе недопустимо.
- Вход по email/паролю. JWT access token (Bearer) действует **30 минут**; refresh-токена нет. Пароли хранятся только как Argon2id-хеш.
- Email нормализуется (trim + lowercase), уникален независимо от регистра. Пароль 8–64 символа, email — корректный формат, максимум 254 символа.
- Чужую бронь нельзя получить или изменить: возвращать `404 BOOKING_NOT_FOUND`, не раскрывая её существования. Отсутствующий/истёкший/некорректный токен → `401`; недостаточная роль для admin API → `403`.
- Администратор создаётся только seed-командой, с учётными данными из переменных окружения (без хардкода секретов).

## 4. Модель данных

### User

| Поле | Тип | Правило |
|---|---|---|
| id | UUID | PK |
| email | string | обязательный, уникальный case-insensitive |
| password_hash | string | Argon2id |
| role | enum | `USER`, `ADMIN` |
| created_at | UTC datetime | серверное время |

### Room

| Поле | Тип | Правило |
|---|---|---|
| id | UUID | PK |
| name | string | 3–50 символов после trim, уникально без учёта регистра |
| capacity | integer | 2–10 включительно |
| price_per_30min_kopeks | integer | 10000–200000 включительно |
| is_active | boolean | default `true` |

### Booking

| Поле | Тип | Правило |
|---|---|---|
| id | UUID | PK |
| user_id | UUID | FK → User.id, обязателен |
| room_id | UUID | FK → Room.id, обязателен |
| title | string | 3–60 символов после trim |
| booking_date | date | формат `YYYY-MM-DD` |
| start_time | time | формат `HH:mm`, шаг 30 минут |
| duration_minutes | integer | строго одно из `30, 60, 90, 120` |
| attendees | integer | от 1 до `Room.capacity` |
| total_price_kopeks | integer | снимок цены на момент создания |
| status | enum | см. раздел 6 |
| created_at, updated_at | UTC datetime | серверное время |
| expires_at | UTC datetime | `created_at + 15 минут` |

Связи: User **1:N** Booking и Room **1:N** Booking. Физическое удаление пользователя/комнаты при наличии броней не реализовывать; `DELETE` комнаты устанавливает `is_active=false` и сохраняет брони.

**Технические таблицы**, не считающиеся бизнес-сущностями: `outbox_events` для надёжной публикации запросов в Kafka и `processed_payment_events` для дедупликации результатов. Для `payment-service` разрешена небольшая отдельная SQLite-БД с Docker volume для дедупликации запросов; прямой доступ к PostgreSQL backend запрещён.

## 5. Правила бронирования

Все правила дат и часов рассчитываются по зоне **Europe/Moscow** (сервер хранит timestamps в UTC).

1. `booking_date` — только **будний день** (пн–пт), начиная с **завтра** и заканчивая **сегодня + 14 календарных дней**, обе границы включены. «Сегодня» определяется в Europe/Moscow.
2. Часы работы: `09:00–21:00`. Старт только `09:00, 09:30, ..., 20:30`; окончание может быть ровно `21:00`, но не позднее.
3. Длительность строго 30/60/90/120 минут. Число участников — целое от 1 до вместимости комнаты.
4. Новое бронирование допускается только для `Room.is_active=true`. Отключение комнаты не изменяет уже созданные брони.
5. Запрещены пересекающиеся брони **одной комнаты на одну дату**, если существующая бронь в статусе `CREATED`, `PAYMENT_PENDING` или `CONFIRMED`; для первых двух состояний предварительно применяется истечение срока. Подтверждённая бронь не истекает. Интервалы полуоткрытые: `[start, end)`; брони `10:00–11:00` и `11:00–12:00` не конфликтуют.
6. Брони со статусом `CANCELLED`, `PAYMENT_FAILED`, `EXPIRED` слот не занимают. Просроченную `CREATED`/`PAYMENT_PENDING` надо переводить в `EXPIRED` перед проверкой занятости (ленивая очистка при операциях + периодический фоновый проход, например раз в минуту).
7. `total_price_kopeks = Room.price_per_30min_kopeks × (duration_minutes / 30)`. Цена фиксируется при создании и не меняется, если администратор изменил тариф комнаты.
8. Создание двух конкурентных броней одного слота не может приводить к двойному резервированию: в транзакции PostgreSQL сериализовать проверку/вставку блокировкой строки Room (`SELECT ... FOR UPDATE`) либо эквивалентным корректным механизмом.

## 6. Конечный автомат брони

Начальный статус после успешного `POST /bookings` — `CREATED`. На оплату есть 15 минут с момента создания, включая время обработки платежа. Если серверное время `now >= expires_at`, срок уже истёк.

| Исходное состояние | Событие | Новое состояние |
|---|---|---|
| CREATED | пользователь нажал «Оплатить» | PAYMENT_PENDING |
| CREATED | пользователь отменил | CANCELLED |
| CREATED | наступило `expires_at` | EXPIRED |
| PAYMENT_PENDING | получен `SUCCESS` до истечения срока | CONFIRMED |
| PAYMENT_PENDING | получен `FAILED` до истечения срока | PAYMENT_FAILED |
| PAYMENT_PENDING | пользователь отменил | CANCELLED |
| PAYMENT_PENDING | наступило `expires_at` | EXPIRED |

`CONFIRMED`, `PAYMENT_FAILED`, `CANCELLED`, `EXPIRED` — терминальные состояния. Повторные действия на терминальной брони → `409 INVALID_STATUS_TRANSITION` (кроме повторного получения данных). Повторное сообщение Kafka о прежнем платеже **не меняет состояние**, не создаёт повторных эффектов; если бронь уже отменена/истекла, поздний `SUCCESS` игнорируется и логируется. Запрос `/pay` повторно в `PAYMENT_PENDING` → `409` и не создаёт повторного запроса в Kafka.

В момент обработки событий сначала проверять/применять истечение срока по серверному времени. Для тестирования часов необходимо предусмотреть инъекцию `Clock` в доменную логику (мок/fixture), без публичного изменения времени на продакшен-API.

## 7. REST API (основной backend)

Базовый префикс `/api`; JSON, заголовок `Authorization: Bearer <token>`, кроме регистрации/логина/health.

| Метод | URL | Роль | Ожидаемый результат |
|---|---|---|---|
| POST | `/auth/register` | аноним | `201` + user без hash |
| POST | `/auth/login` | аноним | `200` + `access_token`, `token_type=bearer` |
| GET | `/users/me` | USER/ADMIN | `200` + текущий user |
| GET | `/rooms` | USER/ADMIN | `200` + активные комнаты; ADMIN с `include_inactive=true` видит все; для USER параметр принимается, но не расширяет результат |
| GET | `/rooms/{id}` | USER/ADMIN | `200` + комната; запрос неактивной комнаты от USER → `404 ROOM_NOT_FOUND`, ADMIN получает её с `200` |
| POST | `/rooms` | ADMIN | `201` + room |
| PATCH | `/rooms/{id}` | ADMIN | `200` + room; меняются name, capacity, price, is_active; `{}` → no-op `200`, явный `null` → `422 VALIDATION_ERROR` |
| DELETE | `/rooms/{id}` | ADMIN | `204` без тела; устанавливает `is_active=false`, повторный вызов тоже `204`; неизвестная комната — `404 ROOM_NOT_FOUND` |
| POST | `/bookings` | USER/ADMIN | `201` + booking (`CREATED`) |
| GET | `/bookings` | USER/ADMIN | `200` + свои брони, admin — все; сортировка `created_at DESC` |
| GET | `/bookings/{id}` | владелец/ADMIN | `200` + booking |
| POST | `/bookings/{id}/pay` | владелец/ADMIN | `202` + booking (`PAYMENT_PENDING`) |
| POST | `/bookings/{id}/cancel` | владелец/ADMIN | `200` + booking (`CANCELLED`) |
| GET | `/health/live` | аноним | `200 {"status":"ok"}` если процесс жив |
| GET | `/health/ready` | аноним | `200 {"status":"ok"}` если доступна основная БД; недоступна БД → `503 DATABASE_UNAVAILABLE`; Kafka/payment — **не** блокирующая зависимость |

Пример создания брони:

```json
{
  "room_id": "UUID",
  "title": "Планёрка команды",
  "booking_date": "2026-11-10",
  "start_time": "10:00",
  "duration_minutes": 60,
  "attendees": 3
}
```

В ответе Booking обязательно содержать `id`, `room_id`, `user_id`, `booking_date`, `start_time`, `end_time` (вычисляемое поле), `duration_minutes`, `attendees`, `total_price_kopeks`, `status`, `expires_at`.

Общая форма ошибок (для ошибок приложения):

```json
{ "error": { "code": "TIME_SLOT_OCCUPIED", "message": "Выбранный слот занят" } }
```

- `401 UNAUTHORIZED`: нет/плохой/просроченный JWT, неверный пароль.
- `403 FORBIDDEN`: пользователь вызывает admin API.
- `404 ROOM_NOT_FOUND` / `BOOKING_NOT_FOUND`: отсутствует ресурс/скрыт чужой ресурс.
- `409 EMAIL_ALREADY_EXISTS`, `ROOM_NAME_ALREADY_EXISTS`, `ROOM_INACTIVE`, `TIME_SLOT_OCCUPIED`, `INVALID_STATUS_TRANSITION`.
- `422 VALIDATION_ERROR`: неверные типы, поля, диапазоны, будние дни, некорректное рабочее время; возвращать массив ошибок по полям.
- `503 PAYMENTS_UNAVAILABLE`: только `/pay` при `PAYMENT_MODE=disabled`.

**Приоритет для create booking:** аутентификация → схема запроса → существование комнаты → активность комнаты → остальные бизнес-ограничения → конфликт слота. Так ошибки воспроизводимы. Доступ к чужим броням всегда маскируется под 404.

Списки в MVP не имеют параметров пагинации или лимитов и возвращают весь доступный вызывающему набор. `/rooms` фильтруется по правилам роли и сортируется по `name ASC` без учёта регистра, затем `id ASC`; `/bookings` фильтруется по владельцу для USER и сортируется по `created_at DESC`, затем `id DESC`. Проверки списков должны использовать небольшой контролируемый набор данных и не передавать несуществующие параметры пагинации.

## 8. Контракт Kafka и платёжный симулятор

Топики:

- `payment.requests.v1` — backend публикует `PaymentRequested`.
- `payment.results.v1` — payment-service публикует `PaymentSucceeded` / `PaymentFailed`.

Ключ сообщения (Kafka key) — `booking_id`. JSON schema `version=1`:

**PaymentRequested**

```json
{
  "event_id": "uuid-request",
  "event_type": "PaymentRequested",
  "version": 1,
  "occurred_at": "2026-11-01T10:00:00Z",
  "booking_id": "uuid-booking",
  "amount_kopeks": 100000,
  "currency": "RUB"
}
```

**PaymentSucceeded / PaymentFailed**

```json
{
  "event_id": "uuid-result",
  "event_type": "PaymentSucceeded",
  "version": 1,
  "occurred_at": "2026-11-01T10:00:01Z",
  "correlation_id": "uuid-request",
  "booking_id": "uuid-booking"
}
```

Payment-service потребляет запрос, симулирует `success`, `failure` или `no_response` и (кроме `no_response`) публикует ровно один *логический* результат. Сетевые ретраи и повторные доставки Kafka возможны: `event_id` дедуплицируется; повторная обработка не создаёт новой оплаты и не меняет терминальную бронь. Результат по другому `booking_id` не должен менять исходную бронь. Микросервис не пользуется базой основного приложения.

Некорректный, дублированный, несопоставимый или поздний результат оплаты не меняет состояние брони. Backend создаёт log record со стабильными структурированными полями `event=payment_result_ignored` и `reason`, где `reason` — одно из `invalid_contract`, `duplicate`, `booking_or_correlation_mismatch`, `terminal_status`. Текст сообщения и формат вывода логгера контрактом не являются.

В `TEST_MODE=true` разрешается параметр `test_scenario: success | failure | no_response` в теле `/bookings/{id}/pay` для контролируемой проверки ветвей; backend передаёт его в `PaymentRequested` как необязательное поле `test_scenario`, которое payment-service учитывает только при собственном `TEST_MODE=true`. Во всех прочих режимах поле отклоняется как неизвестное (422), а сервис по умолчанию отвечает `success`. Это только симуляция, никаких реальных денег.

`outbox_events` создаётся атомарно с переходом в `PAYMENT_PENDING`; отдельный фоновый отправитель публикует события и повторяет попытки при падении брокера. В `stub` обработка результата идёт через тот же доменный обработчик, что применяется к `payment.results.v1`. В `kafka` при отсутствии broker backend/фронт доступны, а ожидающая оплата позже станет `EXPIRED`.

## 9. Frontend

Четыре экрана: (1) регистрация/вход; (2) список и карточки активных комнат; (3) форма бронирования выбранной комнаты; (4) «Мои брони» со статусом и действиями «Оплатить» / «Отменить». Для `ADMIN` — дополнительная простая форма списка/редактирования комнат. Модальные окна и сложный календарь не обязательны.

- Корректно показывать ошибки полей, 401/403/404/409, состояние загрузки.
- Блокировать кнопки во время запроса (это **не** заменяет серверную защиту от повторов).
- Отображать цену, сроки и читаемые статусы; после `/pay` обновлять бронь опросом `GET /bookings/{id}` раз в секунду, не более 10 секунд, затем показывать `«Оплата обрабатывается»` без ложного утверждения об успехе.
- При `PAYMENT_MODE=disabled` показывать сообщение о временной недоступности оплаты.
- Доступность автотестам: семантические labels, `role`, текст кнопок, стабильные `data-testid` для критичных элементов: `login-submit`, `room-card-{id}`, `booking-submit`, `booking-status`, `pay-button`, `cancel-button`, `form-error`.
- Закрытые страницы требуют авторизации. Токен хранить на клиенте без хранения пароля; logout очищает локальную авторизацию.

## 10. Развёртывание и тестовые данные

Команды должны быть задокументированы в README:

```bash
# Только основной продукт: frontend + backend + db, оплата через встроенный stub
 docker compose up -d --build

# Интеграционный режим: дополнительно брокер и отдельный payment-service
 PAYMENT_MODE=kafka docker compose --profile payments up -d --build

# Остановить только микросервис: всё остальное продолжает работать
 docker compose stop payment-service

# Посмотреть OpenAPI
 # http://localhost:8000/docs
```

Реализовать `seed` и `reset-test-data` (только dev/test, с подтверждённой безопасной проверкой окружения). Начальные комнаты: `Small` (2 места, 300 ₽/30 мин), `Medium` (4 места, 500 ₽/30 мин), `Large` (8 мест, 800 ₽/30 мин); у каждой `is_active=true`. Один seed-пользователь `USER` и один `ADMIN` с паролями из `.env.example` исключительно для локальной разработки. Никаких подготовленных броней — тесты создают свои данные и чистят их после себя.

`GET /health/ready` не должен возвращать 503 только из-за остановки Kafka/payment-service. Миграции применяются автоматически при запуске backend или документированной командой, но не вручную с хоста.

## 11. Минимальный набор тест-дизайна (входит в критерии приёмки)

### Классы эквивалентности

- Дата: допустимый будний день в горизонте / сегодня и прошлое / дальше 14 дней / выходной / невалидная строка.
- Время: допустимый шаг 30 минут / внутри рабочего дня, но не по сетке / до открытия / окончание после 21:00.
- Длительность: одно из 4 допустимых значений / другие числа / дробные значения / строка вместо числа.
- Участники: допустимо / 0 / больше вместимости / нецелое.
- Бронирование: свободный слот / занятый интервал / соседний непересекающийся интервал.
- Авторизация: валидный JWT / без JWT / просроченный / чужой ресурс / USER на admin API.

### Граничные значения

| Поле/условие | Обязательные проверки |
|---|---|
| attendees, комната capacity=4 | `0`, `1`, `4`, `5` |

### Переходы состояний

Обязательно проверить все семь разрешённых переходов из раздела 6, а также минимум четыре запрещённых: `CONFIRMED→pay`, `CANCELLED→pay`, `PAYMENT_FAILED→cancel`, `EXPIRED→pay`. Проверить, что `SUCCESS` после `CANCELLED`/`EXPIRED` игнорируется.

### Конкурентность, Kafka, моки

- Два одновременных POST на один слот → ровно одно `201`, второе `409`.
- Два одинаковых `PaymentSucceeded` c одним `event_id` → один переход/эффект.
- `PaymentFailed` и затем поздний `PaymentSucceeded` → статус не меняется после терминального исхода.
- Остановленный payment-service при живой Kafka → основное API работает, оплата в `PAYMENT_PENDING` и со временем `EXPIRED`.
- `PAYMENT_MODE=stub` → успешная и неуспешная оплата без Kafka.
- `PAYMENT_MODE=disabled` → 503 только для pay.
- Тестовые моки: подменить `PaymentGateway`/publisher и `Clock`, проверить success/failure/no_response, дубли и таймаут; контракт Kafka проверить отдельным интеграционным тестом с настоящим брокером.

## 12. План покрытия за 1–2 недели и Definition of Done

**Рекомендуемая цель: 35–45 осмысленных автотестов**, а не сотни похожих кейсов:

- API/авторизация/CRUD/валидация/пересечения: 22–28 (pytest + httpx).
- UI: 5–7 основных E2E (Playwright).
- Состояния/время/конкурентность: 5–7 API или unit.
- Payment/Kafka/idempotency: 4–6 интеграционных тестов (можно добавить во вторую неделю).

Рекомендуемая последовательность: сначала API + fixtures + seed, затем UI, затем mock/stub, после — Kafka и интеграции. Тесты должны запускаться отдельно от исходников, иметь понятные отчёты (например Allure), не опираться на порядок исполнения и не использовать произвольные `sleep` для ожидания смены статуса.

**Готово, когда:**

1. `docker compose up -d --build` поднимает работающее приложение без Kafka/payment-service.
2. Регистрация, login, комнаты, создание/список/отмена броней работают через UI и API.
3. Все ограничения из раздела 5 реализованы на сервере, а не только во фронтенде.
4. Документированные коды ошибок и статусы воспроизводимы.
5. В режиме `stub` бронь может завершиться успехом или отказом; в `disabled` оплата недоступна без падения основного приложения.
6. В режиме `kafka` отдельный payment-service обрабатывает запрос, возвращает событие и меняет состояние брони; его можно остановить независимо.
7. Повторы/поздние события не ломают конечный автомат; конкурентное резервирование не даёт двойной брони.
8. Есть OpenAPI, миграции, README, `.env.example`, seed/reset для test, health endpoints и изолированные тестовые данные.
9. Набор автотестов демонстрирует классы эквивалентности, границы, таблицу решений и переходы состояний.

**Строгое ограничение объёма:** любые новые бизнес-сущности, функции настоящей оплаты, полноценные календарные виджеты, email-сервисы и дополнительная микросервисная архитектура — только после завершения этого MVP.
